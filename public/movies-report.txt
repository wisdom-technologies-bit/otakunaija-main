2. UPCOMING CLASSIFICATION AND COUNTDOWN

Classification is entirely time-based on episodes.publishedAt:

Source: lib/db/queries.ts, lines 225-242.

const _getUpcomingEpisodes = cache(
  unstable_cache(
    async (limit: number) => db
      .select({ episode: episodes, series, creator: creators })
      .from(episodes)
      .leftJoin(series, eq(episodes.seriesId, series.id))
      .leftJoin(creators, eq(series.creatorId, creators.id))
      .where(gt(episodes.publishedAt, new Date()))
      .orderBy(asc(episodes.publishedAt))
      .limit(limit),
    ['upcoming-episodes'],
    { revalidate: 60, tags: ['episodes-upcoming'] }
  )
)

export async function getUpcomingEpisodes(limit = 12) {
  return _getUpcomingEpisodes(limit)
}

Released/new content uses the inverse condition:

Source: lib/db/queries.ts, lines 197-223.

.where(lte(episodes.publishedAt, new Date()))
.orderBy(desc(episodes.publishedAt))

Thus:
- upcoming means publishedAt is strictly later than the query's current time;
- released means publishedAt is less than or equal to the current time;
- the switch happens automatically when wall-clock time reaches publishedAt;
- there is no status update or cron job required for the classification;
- the query cache is configured to revalidate after 60 seconds, so the displayed classification can remain cached briefly;
- the upcoming query is ordered by the scheduled timestamp, earliest first.

3. SERIES / SEQUENTIAL EPISODE ASSUMPTIONS

Yes. The current schema assumes every playable record is an episode belonging to a series:
- episodes.seriesId is NOT NULL and references series.id.
- episodes.episodeNumber is NOT NULL.
- every episode detail route is nested as /episodes/{series-slug}/{episode-slug}.
- the watch page requires a series context and returns “Series Not Found” if the joined series is absent.

There is no existing first-class standalone-video concept in the inspected schema or route structure. No movie, OVA, or special type is represented separately. A movie could only be forced into the episodes table as an episode with a required seriesId and episodeNumber, which would make it structurally an episode rather than a standalone item.

The schema does not enforce numeric consecutiveness at the database level: episode_number is required but there is no unique(series_id, episode_number) constraint and no check constraint requiring 1,2,3,... However, the application treats the value as a meaningful sortable sequence.

It displays a grid of SeriesCard components, not individual playable records. It filters and paginates the series table by series status/genre/sort. For each series it derives episodeCount by calling getLatestEpisodeNumber, which is MAX(episodes.episodeNumber), not a count of arbitrary media items. A movie represented only as an episode would not appear as a movie card; it would be folded into a parent series and affect that series’ latest-number metadata. A true standalone movie cannot fit this query as-is because seriesId is required and the route is series-oriented. It would need a separate catalog model/query or an explicit special-case design.

BOTTOM LINE
The upcoming feature did not add a new schema field: it repurposes publishedAt as a future scheduled release timestamp. The current content model is strictly series/episode-shaped. Browse is series-only; new-releases is episode-plus-series-only; and navigation, sorting, search, metadata, notifications, progress, editor, and card components all assume episodeNumber is present and meaningful. A movie/OVA/special would require either an explicit new content model/type and generic routing, or deliberate special-casing throughout these surfaces; it cannot be cleanly introduced as a standalone item using the current schema and routes alone.
