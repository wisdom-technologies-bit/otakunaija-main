```ts
import { NextResponse, type NextRequest } from "next/server"
import { SESSION_COOKIE, verifySessionToken } from "@/lib/auth"

export async function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl
  if (pathname === "/admin/login") return NextResponse.next()
  if (pathname.startsWith("/admin")) {
    const token = request.cookies.get(SESSION_COOKIE)?.value
    const session = await verifySessionToken(token)
    if (!session) {
      const url = request.nextUrl.clone()
      url.pathname = "/admin/login"
      url.searchParams.set("from", pathname)
      return NextResponse.redirect(url)
    }
  }
  return NextResponse.next()
}

export const config = {
  matcher: ["/admin/:path*"],
}
```
The matcher protects only `/admin/:path*`; API ingestion routes are not protected by proxy and use their own API-key checks.

8. RISKS

- `public/sw.js` is already a root-level service worker and imports an external ad service worker. OneSignal also expects root-scope worker behavior; blindly replacing or duplicating `/sw.js` can break the existing ad integration or cause registration collisions. Inspect the ad provider’s required worker path/scope before adding OneSignal.
- A client-side OneSignal component must be mounted from `app/layout.tsx` or another shared client boundary, but this audit request explicitly prohibits changing the header/shared layout; build instructions should decide whether a separate provider boundary is acceptable.
- There are four relevant insert paths: admin post, admin series, admin episode, AniList/Play series, and AniList/Play episode. Hooking only admin actions will miss API ingestion; hooking only shared `createSeries`/`createEpisode` will miss direct Drizzle inserts in Play routes.
- The admin series/episode inserts and Play inserts have no draft state. `episodes.publishedAt` defaults to now, and posts have no visible draft/status field. A notification trigger should therefore be based on successful insert plus a clear publication policy, not merely on function invocation.
- Play ingest is idempotent/deduplicated but may receive retries and concurrent unique races. Push calls must be idempotent or queued after a confirmed new row, never sent in both the try path and unique-race path.
- Bulk behavior: `/api/play/fill` can process multiple anime/episodes and may call the ingest endpoints repeatedly. Sending synchronously after each insert could create notification storms and slow/fail ingestion.
- Server-side push calls must remain Node/server-only; do not import OneSignal server credentials into client components or edge routes. Current R2 routes explicitly use Node runtime, while most routes do not declare a runtime; choose Node for any server push endpoint/client.
- Existing ad/service-worker scripts, CSP absence, caching (`unstable_cache`), and revalidation mean a push payload can be sent before all public pages/cache entries visibly update unless the insert path also revalidates the relevant public route/cache tags.
- Admin auth is cookie/session based and proxy matcher does not protect `/api/play/*`; those routes rely exclusively on `PLAY_API_KEY`, so protect the key and do not expose push credentials to callers.

FINAL RECOMMENDATION / TRIGGER LOCATIONS

There are three requested content trigger categories, with multiple physical creation points:
1. Blog post: add the post-created trigger immediately after `const post = await createPost(input)` in `app/actions/admin.ts:111` (after the optional news mark-inserted operation is preferable, before revalidation/redirect). There is one discovered local post insert path.
2. New series: add a shared trigger after `await db.insert(series).values(values).returning(...)` succeeds in `app/api/play/anime/route.ts:100-101`, and after `const series = await createSeries(input)` in `app/actions/admin.ts:226` (or centralize both through a notification service). Do not notify on title-match updates or unique-race responses.
3. New episode: add a shared trigger after `await db.insert(episodes).values(values).returning(...)` succeeds in `app/api/play/episodes/route.ts:68-69`, and after `const episode = await createEpisode(input)` in `app/actions/admin.ts:308`. Do not notify on existing `playId` updates or unique-race responses.

Recommended bulk-import approach: do not call OneSignal synchronously per row. Record an outbox/event row transactionally with each genuinely new post/series/episode (including an import/batch ID), then have a protected Node cron/worker drain the outbox, deduplicate by content ID and event type, group a bulk run into one summary notification or bounded batches, retry failures with backoff, and mark events delivered. If an outbox migration is not yet desired, accumulate newly inserted IDs during `/api/play/fill` and send one bounded batch after the import completes, with a hard cap and deduplication; never notify from duplicate/update responses.
